# Decisions

Decisions taken during the 3.0 rebuild where the brief left room for interpretation.
Each entry says what was decided and why. Newest phase last.

## Phase 1 — Architecture

| # | Decision | Why |
|---|----------|-----|
| D-001 | Keep the plugin name ("BookPoint Booking & Appointments"), slug `pointly-booking`, text domain `pointly-booking`, REST namespace `pointly-booking/v1`, table/option prefix `pointlybooking_`, and the 2.x shortcodes and block name `bookpoint/booking-form`. New PHP lives in the `PointlyBooking\` namespace under `includes/` (PSR-4). | Backward compatibility with stored data, saved posts, external links and the WordPress.org listing. |
| D-002 | Development main file stays `bookpoint-v5.php`; `scripts/package-plugin.ps1` renames it to `pointly-booking.php` in the release ZIP (unchanged from 2.x). | Existing packaging and deployment flow. |
| D-003 | Minimum WordPress raised from 6.0 to **6.2**. | Needed for the `%i` identifier placeholder in `$wpdb->prepare()` (safer table names) and React 18 `createRoot` in `wp-element`. |
| D-004 | JSX uses the **classic** runtime (`babel.config.js`), auto-importing `createElement` from `@wordpress/element`. | The automatic runtime needs the `react-jsx-runtime` script handle, which only exists from WP 6.6. |
| D-005 | Database schema version jumps to `6.0.0` (option `pointlybooking_db_version`); the migrator runs only when the stored version differs, under a 5-minute transient lock. Columns and tables are never dropped. | Fixes B-120 (migrations ran on every admin request) while keeping every 2.x column readable. |
| D-006 | Canonical link tables are `agent_services`, `service_categories` and `extra_services`. 2.x data in `service_agents`, `services.category_id` and `service_extras.service_id` is imported once (upgrade from < 6.0.0); afterwards the legacy columns are only written as mirrors (Tools → Sync relations rebuilds them). | 2.x read different link tables in different places, so a staff member could be bookable in one screen and not in another. |
| D-007 | Settings are stored in the `pointlybooking_settings` option (schema-validated). The 2.x key/value table stays as a read fallback and three keys are written through to it. | One validated source of truth without breaking code that still reads the table. |
| D-008 | Payment credentials (`stripe_*`, `paypal_*`, `payments_*`) can be read and changed only by users with `manage_options`; secrets are returned masked (`••••••••1234`) and a masked value sent back means "unchanged". | Staff/manager roles have `pointlybooking_manage_settings`, which must not expose API keys. |
| D-009 | Site administrators (`manage_options`) always hold every `pointlybooking_*` capability through a `user_has_cap` filter. | Sites where the administrator role was never updated (new multisite sites, role editors) would otherwise lose the menu. |
| D-010 | Bookings keep storing site-local `DATETIME` values (`wp_timezone()`), as in 2.x; the site time zone is shown to customers. | Existing data is local time; converting it to UTC would be risky and gains nothing for a single-location business. |
| D-011 | Double-booking protection: MySQL `GET_LOCK` per date plus a full availability re-check inside the lock, for wizard, admin, manage-page reschedules and legacy routes. Staff conflicts are checked across all services. | B-025/B-026: 2.x only checked the same service and had no lock. |
| D-012 | "Any available" staff picks the eligible person with the fewest bookings that day. When no active staff exist, bookings are made against the business (`agent_id` NULL) using the business hours. | Even distribution; keeps single-person businesses working without creating a staff record. |
| D-013 | Extras' `duration_min` is shown to customers but does not lengthen the booking (as in 2.x). The quote returns `duration` (service) and `extras_time` separately. | Changing slot lengths would alter availability for existing sites. |
| D-014 | The manage key rotates after a customer cancels or reschedules (F-183). The new key is written in the same update as the change, before notifications fire, so the email already carries the new link. Keys are 64 hex characters; 40-hex keys from very old releases are still accepted. | Keeps the 2.x security behaviour without the broken-link bug (B-037). |
| D-015 | Customers can cancel/reschedule from the manage page while the booking is pending/confirmed and in the future (reschedule not while awaiting payment). Filter: `pointlybooking_manage_permissions`. | 2.x had no rules at all; this is the safe default and sites can loosen or tighten it. |
| D-016 | The customer portal is now a small React app backed by `/portal/*` REST routes (one-time code by email, 20-minute session token kept in `sessionStorage`). | 2.x used server-rendered forms with session tokens in the URL and page-cache problems. |
| D-017 | Built-in emails are workflows. On upgrade each default workflow is installed unless the site already has an active workflow emailing the same recipient type for that event. | 2.x sent hard-coded emails in addition to custom workflows; upgraded sites must keep receiving them without duplicates. |
| D-018 | Rate limits (per IP): booking creation 10/10 min, quotes/promo 60/10 min, booking status 120/10 min, manage view 60/10 min, manage and portal actions 30/20 per 10 min, portal view 120/10 min. Availability reads are not rate limited (they are cached and would otherwise write a transient on every request). Filter `pointlybooking_rate_limit_enabled`. | Protect write paths without making the calendar slow on sites without an object cache. |
| D-019 | Guests get no REST nonce (anonymous public routes are cache-friendly); logged-in visitors get a `wp_rest` nonce. The front end retries once without the nonce when a cached page carries a stale one. | Full-page caches would otherwise serve expired nonces and break booking for logged-in users. |
| D-020 | All 2.x public REST routes, admin-post actions and admin-ajax actions are kept as thin adapters over the 3.0 services (`Rest\Front\LegacyController`, `Admin\Actions`, `Frontend\LegacyAjax`). The 2.x admin page slugs redirect to the matching 3.0 screen. | "Never remove a feature" — external integrations, bookmarks and cached pages keep working. |
| D-021 | Admin menu diagnostics (`?pointlybooking_menu_debug=1`) and the Tools → BookPoint Tools shortcut are kept; the 2.x "force the menu visible" workaround is dropped. | The workaround re-registered menus that other plugins had removed on purpose; the capability filter (D-009) covers the real cause. |
| D-022 | "Export to PDF" stays a print-optimised HTML report (use the browser's Save as PDF), as in 2.x. | No PDF library bundled; keeps the plugin small. |
| D-023 | Pro-only license helpers moved from `lib/helpers/` to `pro-addon/includes/` (not part of the free WordPress.org build). | `lib/` is removed; the Pro add-on ZIP script copies them from the new place. |
| D-024 | Stripe.js is loaded from `js.stripe.com` only when a customer pays by card (via `@stripe/stripe-js`). This is the only external script and is listed under "External services" in readme.txt. | PCI rules require Stripe.js to be loaded from Stripe; everything else is bundled locally. |
| D-025 | `.ics` calendar files are served by the REST API (`/wizard/bookings/{id}/ics?key=`) as `text/calendar`, protected by the booking's manage key. | Works on every host without rewrite rules. |

## Phase 2 — Design system

| # | Decision | Why |
|---|----------|-----|
| D-026 | Own component library in `src/ui/` for the wizard, manage page, portal and admin. `@wordpress/components` is used only in the block editor sidebar. | An original, consistent look (brief) and small front-end bundles; WP components are admin-styled and heavy on the front end. |
| D-027 | Prefixes: CSS classes `pbk-`, custom properties `--pbk-`. Every component selector is scoped as `.pbk-root .pbk-…` (specificity 0,2,0) and resets the properties themes usually override (margins, text-transform, shadows, borders). | Survives aggressive theme and page-builder CSS without `!important`. |
| D-028 | Overlays (modal, drawer, popover, tooltip, toast) render into a portal container that also carries `.pbk-root`, the theme attribute and the brand variables, created synchronously during render. | Portals would otherwise lose the scoped styles and colours; synchronous creation lets focus traps attach in the same commit. |
| D-029 | The brand scale 50–900 is generated in JavaScript by mixing in OKLab and applied as inline custom properties on the root; text on the brand colour and brand-coloured text are adjusted until they reach 4.5:1. | Live preview without rebuilding, and any colour a business picks stays readable (WCAG AA). |
| D-030 | Token and base CSS are imported by `ThemeRoot`, not by the `src/ui` barrel file; `package.json` marks only CSS as side-effectful. | Webpack skips side-effect-free barrel files, which silently dropped the base styles. |
| D-031 | Front-end dark mode follows the booking form design setting (off / on / follow the visitor's system). Admin dark mode is a per-browser toggle stored in `localStorage["pointlybooking_theme"]` (2.x key). | Matches F-042 and F-150; a dark booking form on a light theme would look broken, so it stays opt-in. |
| D-032 | Custom calendar, date picker and time slots instead of FullCalendar and `@stripe/react-stripe-js`; only `@stripe/stripe-js` (loader) remains. | Smaller bundles, one visual language, full keyboard support we control. |
| D-033 | Linting: WordPress ESLint/Stylelint presets, with three JSDoc rules for destructured props, `no-descending-specificity` (state selectors) and the class pattern (BEM `__`/`--` allowed) relaxed in `.eslintrc.js` / `.stylelintrc.json`. | Those rules produced hundreds of false positives without catching bugs. |
| D-034 | A design-system gallery (`?page=pointlybooking_dashboard&pbk_ui_kit=1`) ships as a lazy admin chunk and only renders when `WP_DEBUG` is on. | Visual QA and screenshots for every component and state without affecting production pages. |

## Phase 3 — Booking wizard

| # | Decision | Why |
|---|----------|-----|
| D-035 | The wizard is a single stateful component (`src/front/wizard/Wizard.js`) driven by pure functions in `flow.js` (which steps apply, staff/services in scope, price preview, validation) rather than a step-per-route router. | The visible step list depends on live data (staff count, location count, payment methods) and must recompute on every change without losing state; a router adds indirection for no benefit here. |
| D-036 | Card payment (`StripePayment.js`, `@stripe/stripe-js/pure`) is a separate lazy chunk, loaded only when the customer picks "Card". The wizard itself is also a lazy chunk, prefetched on button hover/focus and on browser idle. | Stripe.js is the plugin's only external script (D-024); most bookings never reach the payment step, and most page loads never open the wizard at all. |
| D-037 | Availability requests are cached per (service, staff, location) in a module-level `Map` (`api.js`) and the day before/after the selected one is prefetched after a day loads. | Repeated back/forward through the calendar and the month↔day round trip reuse one request instead of refetching. |
| D-038 | On a 409 (slot just taken), the wizard clears the availability cache, drops back to the date/time step and shows the server's message instead of resubmitting. | The user must see a fresh calendar; retrying the same request would fail again. |
| D-039 | Formatting (`context.js`) treats booking times as wall-clock strings in the business time zone: dates are parsed as UTC-with-the-local-numbers and never shifted by the visitor's offset (`shared/format.js` `parseLocal`). A one-line notice appears when the visitor's zone differs. | Matches the PHP side, which stores and returns site-local `DATETIME` (D-010); converting in JS would show the wrong hour to visitors in another zone. |
| D-040 | The manage page and customer portal are a third bundle (`src/manage/`) sharing `src/ui` and the wizard's `context.js`, not part of the `front` bundle. | The manage page and portal are visited directly (not through the wizard) and should not force wizard code onto every front-end page load. |
| D-041 | The portal session token lives in `sessionStorage` (not the URL, not `localStorage`); the manage page updates the address bar's `key` parameter in place after every rotation (D-014) instead of reloading. | Keeps the 2.x portal security model (short-lived, per-tab) while fixing its URL/cache problems (D-016) and never showing a dead link after a change. |
| D-042 | Local dev: a `mailpit` service in `.dev/docker-compose.yml` plus a must-use plugin routing `wp_mail()` to it, so outgoing email (booking confirmations, portal codes) can be asserted on in end-to-end tests via its HTTP API. | Verifies real behaviour (B-050 fix, F-184 one-time code) instead of trusting the code by inspection. |

## Phase 4 — Admin app

| # | Decision | Why |
|---|----------|-----|
| D-043 | Client-side routing (`src/admin/router.js`) reads/writes `page`/`tab`/`view`/`id` query params via `history.pushState`, layered on top of WordPress's own server-rendered admin submenu links (`Admin\Menu`) rather than replacing them. | Keeps every admin URL bookmarkable and compatible with the 2.x deep-link redirects (D-020), while giving the SPA instant in-app navigation. |
| D-044 | The admin shell (`Shell.js`) reclaims the WordPress `.wrap` padding with a negative margin instead of unhooking WordPress's own chrome (admin bar and left menu stay). | An edge-to-edge "app" feel (F-042) without fighting WordPress's admin CSS or breaking other plugins' admin-notice placement. |
| D-045 | Dashboard's "Bookings over time" chart is a hand-built inline SVG bar chart (`MiniChart.js`), not a charting library. | Zero-dependency bundles (brief); the chart is a single bar series and doesn't need a general-purpose library. |
| D-046 | Reorderable lists (services, categories, extras, form fields, booking-form steps, and per-scope field layouts) share one small `useDragReorder` hook built on native HTML5 drag-and-drop, not a drag-and-drop library. | One ~30-line hook covers every list in the app; a library would add a dependency for behaviour this simple. |
| D-047 | The admin calendar (month/week/day/list) is hand-built, not FullCalendar: month view is a day-grid with event chips; week/day view is an absolutely-positioned time grid with a greedy lane-packing algorithm for overlapping events; drag-and-drop reschedule sends a `PATCH` to the same booking endpoint the drawer's reschedule panel already uses. | Matches D-032 (no calendar library); reusing the booking `PATCH` endpoint means the server's conflict/capacity validation (D-011) always applies, even to a drag. |
| D-048 | Image fields (services, categories, extras, staff, locations, booking-form step art) share one `MediaPicker` component that opens the native `wp.media()` frame; there is no custom media browser. | `wp_enqueue_media()` already ships the full WordPress media library UI; rebuilding it would duplicate core functionality for no benefit. |
| D-049 | Weekly-hours editing has two different components for two different data shapes: `WeekdayHours` edits the legacy single-range-per-day override (`schedule_json`, used by a service's, agent's or location's custom hours) as a `{day: "HH:MM-HH:MM"}` map; the Settings → Schedule tab edits the full `{day: [{start,end,breaks}]}` shape the global schedule API supports (multiple intervals and breaks per day, F-120). | The two REST shapes are genuinely different; collapsing them into one editor would either lose the global schedule's multi-interval/breaks capability or force it onto the simpler per-entity override, which no UI needs. |
| D-050 | The Booking Form Designer's step preview is a small representative card (chosen art icon + title/subtitle + accent colour), not a live-embedded copy of the real front-end wizard. Its draft autosaves to `localStorage` (F-155) with a restore/discard banner. | The real wizard depends on the front bundle's own context and data-fetching (D-035); embedding it in the admin bundle would pull front-end code into admin and still not be pixel-accurate through an iframe boundary. The wizard itself remains the single source of truth for what customers see. |
| D-051 | Customers CSV import/export (F-115/F-116) stays a real `admin-post.php` form submission (full-page redirect with a `pbk_notice` query flag the React screen reads once on mount and clears), not a REST/fetch upload; system report and settings JSON export/import (Tools tab) use REST with a client-side `Blob` download and `FileReader`-driven POST. | CSV parsing already lives server-side in `Transfer::import_customers()` (2.x code, kept per D-020); re-implementing it as a fetch upload would duplicate validation for no gain, while JSON is small enough to round-trip through REST directly for a nicer no-reload UX. |
| D-052 | The REST client (`shared/api.js`) unwraps the `{status:'success', data}` envelope to just the inner `data`. Endpoints that additionally return a top-level `message` (2.x-shaped `Controller::message()` responses, used by the Tools actions) have their toast text authored on the client instead of echoing `result.message`, which the unwrap silently drops. | Keeps one client-side response contract for the whole admin app instead of special-casing the handful of endpoints with a legacy shape. Caught by testing every Tools action against the live REST API rather than trusting the code by inspection (same practice as D-042). |
| D-053 | `window.pointlybooking_ADMIN.today` (site-local `Y-m-d`, `Support\Dates::today()`) was added to the admin boot payload. | The calendar screen's "Today" button and today-highlight need the server's notion of today at mount, before any REST call has returned it. |
| D-054 | The notification editor's "insert a smart variable" appends the token to whichever subject/message field was last focused (tracked via a ref), rather than inserting at the caret position. | A caret-accurate insert needs a rich-text control the design system doesn't have yet; append-on-click is predictable and covers the common case of building the message first, then adding tokens. |
